# keihan_tracker の信頼性

このドキュメントでは、keihan_tracker が返す値を**どこまで信頼してよいか**と、その**根拠となる検証**について説明します。

keihan_tracker は京阪電車の非公式APIラッパーです。京阪が公開している仕様書はなく、APIの意味はデータから読み解いています。そのため「すべて正確」とは言えませんが、**どの値が公式データそのままで、どの値が推定なのか**を区別し、推定の部分は実データで検証しています。

このドキュメントでは、公式APIの `wdfBlockNo` を**WDF番号**と呼びます。WDF番号はライブラリが列車を区別するためにキーにしている番号で、列車番号（「1751号」など）や編成番号とは別です。WDF番号は列車ごとに一意ではなく、別の日には同じ番号が別の列車に割り当てられることがあります（同じ番号でも平日と土休日で列車番号が変わる例があります）。ライブラリは営業日が変わると前日の列車を消すため、日をまたいだ混同は起きません。

> 検証時点：2026年11月8日。各集計の対象期間は本文に記載しています。検証対象のデータは[検証に使ったデータ](#検証に使ったデータ)、位置・履歴・遅延下限の確認結果は[位置座標と遅延下限の検証](#5-位置座標と遅延下限の検証)を参照してください。

v3 の構造・到着予測と始発時刻の調査は2026年11月14日に追記しました。過去の運行集計の対象期間は変えていません。
v2.9 からの書き換えは [移行ガイド](../MIGRATION.md) を参照してください。

## まとめ

*   **走行中の列車の種別・行先・方向・臨時かどうか・遅延 `delay_minutes` は、公式APIの値そのまま**です。別のプロパティ `estimated_delay_minutes` は、120分以上の遅延の下限をライブラリが推定します（[計算方法と限界](#2時間以上の遅延下限推定)）。
*   **これから走る列車の種別は、停車駅からの推定**です。2022年11月〜2026年6月の過去のダイヤ26日分（のべ約3万本）で検証し、走行中の列車のべ1090本では、推定した種別が公式APIの種別と**すべて一致**しました。2026年10月7日〜30日の24日間の運行23,932本では、ライナーを除く**23,717本すべてが一致**しました。ライナーは停車駅から区別できないため、特急または通勤快急と推定されます。
*   **ダイヤが乱れているときも落ちません**。ダイヤに無い列車や、時刻不明の停車駅を含むデータでも動作することを、実際のダイヤ乱れのデータで確認しています。
*   **壊れた位置情報JSONは、列車の状態を変えずに拒否します**。`KeihanAPIError` になり、列車の状態は前回のまま残ります。行先なしのデータや、一時的に誤った方向も、実際に返ってきたデータで動作を確認しています（[公式APIが異常なデータを返したとき](#公式apiが異常なデータを返したとき)）。ただし、WDF番号が重複・再利用される場合は、列車属性や履歴を正しく区別できない制約があります（[WDF番号の重複・再利用](#wdf番号の重複再利用)）。
*   **京阪バスの接近情報は、公式の値をほぼそのまま返します**。壊れた応答は電車と同じ `KeihanAPIError` になります。1停留所の接近情報と1便の発着時刻表を保存して自動テストしていますが、検証範囲は限られ、存在しないバス停名を区別できません（[京阪バスの接近情報](#京阪バスの接近情報)）。
*   **到着予測は `estimate_arrival()` / `tracker.eta()` で取得できます**。遅れ増加・長時間停滞・前詰まりなどでは時刻を伏せ、理由を返します。予測精度を実測したものではありません。情報の古さや画面の表示は、引き続き表示する側で判断してください（[表示する側でやること](#表示する側でやること)）。
*   一方で、停車駅だけでは区別できない種別の組み合わせ（ライナーと特急など）や、ダイヤ乱れ時にダイヤと実際の運行がずれることなど、**原理的に避けられない限界**があります（[分かっている限界](#分かっている限界)）。

`snapshot_dir` のデータは、keihan_tracker で1分に1回 `fetch_pos()` を呼び、`snapshot_dir` を指定して保存したものです。保存するのは、内容が前回から変わったときだけです。ダイヤは、ふだんは1時間に1回取得します。次の時間は取得できていません。

*   10月7日の8時38分まで（保存を始める前）
*   10月12日 14時17分〜17時27分、10月13日 15時6分まで・17時22分〜19時3分、10月14日 7時52分〜8時12分、10月19日 8時40分〜18時1分（取得していたプログラムの停止）
*   10月21日 20時45分〜22日 18時51分（京阪のホームページの休止。[長時間の停止](#公式apiが異常なデータを返したとき)）

このドキュメントで「再生」と書いているのは、保存した位置情報・ダイヤを時刻順に読み込ませ、そのときライブラリがどう動いたかを確かめることです。集計当時は `fetch_pos()` へ読み込ませました。v3 は通信・時計なしの `KHState` に `apply_stations()` → `apply_positions()` → `apply_timetable()` で渡せます。

保存データの取得範囲は11月8日0時35分時点までです。種別照合と運行停止の集計は10月7日〜30日、座標変換とWDF番号の重複走査は10月7日〜11月8日が対象です。検証項目によって対象期間・件数が異なります。

この中には、ダイヤが大きく乱れた日が2日あります。10月8日朝（交野線が止まった）と、10月30日夕方（京阪本線の停電）です（[運行が止まったとき](#運行が止まったとき)）。

## 値ごとの出どころと信頼度

keihan_tracker の値は、次の3種類のどれかから来ています。

*   **位置情報**：公式の `trainPositionList.json`。走行中の列車のリアルタイム情報
*   **ダイヤ**：公式の `startTimeList.json`。その日の全列車の停車駅・時刻
*   **推定**：上の2つから、ライブラリが独自に計算した値

| 値 | 出どころ | 信頼度 | 補足 |
| :--- | :--- | :---: | :--- |
| 種別（走行中） | 位置情報 | ◎ | 公式の値そのまま |
| 行先（走行中） | 位置情報 | ◎ | 公式の値そのまま。行先なし（00）のときはダイヤの終着駅で補い、ダイヤも無ければ `None` |
| 方向（走行中） | 位置情報 | ○ | 公式の値そのまま。ただし公式の値が、列車が現れた直後の1分だけ誤ることがある（下りの運行の約2%。次の取得で直る）。終点に停車中は更新しない |
| 臨時列車かどうか `is_special` | 位置情報 | ◎ | 公式の種別表示に「臨時」が付いているか |
| 遅延 `delay_minutes` | 位置情報 | ◎ | 公式の値そのまま。ただし最大でも120（「2時間以上」と来るため） |
| 遅延の下限 `estimated_delay_minutes` | 位置情報・ダイヤ・履歴から推定 | △ | 120分未満は公式値。120分以上は下限を推定するが、実際の遅延との照合による精度検証は未実施（[計算方法と限界](#2時間以上の遅延下限推定)） |
| 列車番号・両数 | 位置情報 | ◎ | 公式の値そのまま |
| 停車駅・時刻 `stop_stations` | ダイヤ | ○ | ダイヤ通りの値。ダイヤ乱れ時は実際と異なる場合あり |
| 停車時刻の予測 `estimate_arrival()` / `eta()` | ダイヤ・位置情報・履歴から推定 | △ | 元の時刻は発車時刻。signage との比較は実施したが、実際の到着との精度検証は未実施 |
| プレミアムカー・編成番号 | ダイヤ | ○ | ダイヤ上の値 |
| 停車中の駅か次の停車駅 `current_or_next_stop` | 位置情報＋ダイヤ | ○ | 現在位置とダイヤの停車駅から計算。`next_stop` は停車中の駅を含まない次の停車駅 |
| 線路上の位置 `position` | 位置情報から推定 | ○ | 路線図上の座標から判定。`position.station` は通過中も含む |
| 停車中の駅 `stopped_at` | 位置情報＋ダイヤ | ○ | 駅の位置にいて、その駅が停車駅なら停車中。通過駅の位置や、停車駅が分からない（ダイヤに無い列車など）ときは `None` |
| 遅延の増える速さ `delay_growth_rate()`・`is_delay_growing()`・`delay_growing_trains()` | 位置情報から計算 | ○ | `history` の遅延分数を比べるだけ。実データでの本数は[運行が止まったとき](#運行が止まったとき) |
| 同じ位置に留まっている時間 `staying_time` | 位置情報から計算 | ○ | 座標が変わらない時間。駅でも駅間でも増える。位置情報の作成時刻で測るため、APIが止まっている間は増えない。座標が粗いため走行中でも数分は増えることがある |
| 種別（走行前・走行後） | 停車駅から推定 | ○ | 後述の検証あり。一部区別できない組み合わせあり |
| 方向（走行前） | 始発・終着から推定 | ○ | 走行中の列車で公式の値と照合済み |
| 走ったことがあるか `was_active` | 位置情報 | ○ | 観測した位置情報に現れたか。観測を始める前や、取得が途切れていた間に走った列車は `False` |
| 走行中でない列車が `upcoming_trains` に入るか | ダイヤ＋観測を始めた時刻 | △ | `was_active` でなく、予定時刻が最初に位置情報を取れた時刻より後なら入る。運休になった列車も入り続ける |

なお、走行中だった列車が運行を終えると、走行中に取得した種別・方向・行先・路線は引き継がれます。推定値に置き換わることはありません。

停車駅の `time` は公式の `stationDepTime`（発車時刻）です。`fastest_arrivals` の到着時刻という名前も、この発車時刻を比べています。
始発駅は通常 `"-"` で時刻不明ですが、先頭駅に既存の時刻が入るダイヤもあります。補完はしていません（[始発時刻の調査](START_TIMES.md)）。

v3 では駅・列車の `master` は `KHState` です。`trains`・`stations` は索引との整合性を保つため読み取り専用にしました。
状態の適用は `KHState`、通信と終了処理は `KHClient` / `KHTracker` / `KHTrackerSync` が担当します。

上記は、WDF番号で列車を区別できる場合の評価です。WDF番号の重複・再利用がある場合は、一つの列車オブジェクトに異なる列車番号の属性や履歴が混在することがあります（[WDF番号の重複・再利用](#wdf番号の重複再利用)）。

## 検証の内容

### 1. 実データを使った自動テスト

`tests/` に、実際のAPIレスポンスを保存したデータを使った自動テストがあります。GitHub Actions で、Python 3.10〜3.13 の各バージョンについて、push のたびに実行しています。

テストには、次の実データを使っています。

*   2026年10月6日（火）21時台の位置情報・ダイヤ（平日ダイヤ。走行中の列車を含む）
*   Wayback Machine から保存した2022年11月〜2026年6月の26日分・28スナップショットのダイヤ（平日・土休日を含む）。うち25件は位置情報も保存
*   2026年10月7日〜10日に `snapshot_dir` で保存した、公式APIの異常な位置情報9件（`tests/fixtures/irregular/`）。ダイヤは保存していないため、10月6日の平日ダイヤと組み合わせています

通常の `python -m pytest tests -q` で、上記の全データをネットワークに接続せずに検証します。行先と方向の整合性は現在の平日データと全28アーカイブが対象で、出町柳行きは上り（京都方面）、淀屋橋・中之島行きは下り（大阪方面）であることを確認します。ダイヤがある走行中の列車では、推定方向と公式の方向も照合します。ダイヤに無い列車は推定方向を求められないため、行先と公式の方向の整合性を検証します。

アーカイブの元データは `tests/fixtures/wayback/` に圧縮して保存し、`manifest.json` に取得元URL・取得日時・列車数・元データのSHA-256を記録しています。26日分のダイヤは延べ29,618列車、対応する位置情報は延べ1,097列車です。元データの欠落・改変も通常のテストで検知します。

v3 の同値性テストは、v2で保存した全列車・全駅の出力と照合します。期待値（`tests/fixtures/equivalence/`）は作り直していません。
取得結果・監視ループ・同期版・バスクライアントのキャッシュと寿命も、通信や実際の待ち時間を使わずにテストしています。

### 2. 停車駅からの種別推定の検証

走行前の列車には、公式データに種別が含まれません。そのため、停車駅のパターンから種別を推定しています。この推定を、次の4つの方法で検証しています。

**(1) 停車パターンの網羅テスト**

テスト用データのダイヤに含まれる停車パターンを、すべて列挙してテストしています。平日ダイヤの99通りと、過去のダイヤにだけある23通り、`snapshot_dir` で保存したダイヤで見つかった1通りが対象です。どのパターンが、どの種別と推定されるべきかを1つずつ確認しています。

**(2) 公式の停車駅案内図との照合**

京阪公式の停車駅案内図を、テストの中に書き写しています。推定した種別が案内図と矛盾しないことを、全列車について確認しています。

**(3) 過去のダイヤと公式の種別との照合**

Wayback Machine（インターネットアーカイブ）に保存されていた過去のダイヤ26日分（スナップショット28件）を使って検証しました。期間は2022年11月〜2026年6月で、のべ約3万本の列車を含みます。

*   走行中だった列車のべ1090本について、停車駅から推定した種別と公式APIの種別を比べました。結果は、**食い違い0本**です。普通・区間急行・準急・通勤準急・急行・快速急行・通勤快急・特急・快速特急 洛楽・ライナーの、すべての種別を含みます。ライナーは特急と推定されるため、特急として扱っています。
*   土休日ダイヤも含めて、快速特急 洛楽の本数が実際の運行（平日2本・土休日8本）と一致することも確認しています。

**(4) 24日間の運行と公式の種別との照合**

2026年10月7日〜30日に `snapshot_dir` で保存した位置情報とダイヤを使って検証しました。運行（同じWDF番号が続けて現れる区間）23,953本のうち、ダイヤのある23,932本について、ダイヤの停車駅から推定した種別を、公式APIの種別と比べました。平日・土休日の両方と、臨時列車・ダイヤ乱れの日を含みます。

推定には、運行が現れた時点で最新のダイヤを使います。ただし4時〜5時30分に現れた運行は、その日の5時30分までに取れた最新のダイヤを使います。始発前は公式のダイヤがまだ前の日のもののことがあり、ライブラリは今日のダイヤが取れるまで取り直して、取れたダイヤで推定し直すためです（[ダイヤ切替前の早朝](#公式データにない情報確認できていないこと)）。

*   **ライナーを除く23,717本すべてで、種別が一致**しました。
*   **ライナー215本**は、停車駅から区別できないため、特急（158本）または通勤快急（57本）と推定されました。通勤快急と推定されたのは樟葉始発のライナーで、停車駅が通勤快急とまったく同じです（[停車駅だけでは区別できない種別](#停車駅だけでは区別できない種別)）。快速急行とは守口市に停車するかどうかで区別でき、快速急行と推定されたライナーはありませんでした。
*   臨時列車30本は、すべて一致しました。10月17日の淀川花火大会の臨時列車4本や、週末に淀を発着する臨時列車、香里園発淀行きの臨時普通を含みます。
*   ダイヤに無い列車は21本です。6本は10月19日の1時台に走ったもの、15本は10月30日の停電のあとの運転整理で走ったものです。運転整理では、同じWDF番号（32768）が別の列車に次々と使われました。

### 3. ダイヤ乱れ時のデータでの動作確認

過去のデータには、ダイヤ乱れのときのものが含まれていました。たとえば、2026年4月28日の淀屋橋〜枚方市間の停電や、2025年3月21日の車両交換（淀屋橋9:24発の準急出町柳行きを萱島で打ち切り、萱島から先は別の編成が臨時列車として運転）です。これらのデータで、次のことを確認しています。

*   位置情報とダイヤがそろったスナップショット25件すべてで、列車の表示・駅の発車標・列車の検索が例外を出さずに動作する。
*   ダイヤに無い列車（のべ7本）は、公式の種別・行先などを正しく保持する。
*   時刻不明の停車駅を含む列車は、停車駅と種別を正しく扱う。

### 4. 公式APIの異常なデータでの動作確認

`tests/fixtures/irregular/` の実データで、次のことを確認しています。

*   末尾にNULが付いたJSON・途中で切れたJSONで `KeihanAPIError` になり、列車の状態が変わらない。次の取得で正常なデータが来れば、続きから動作する。
*   全列車の行先が「00」（行先なし）のデータで、取得が止まらない。
*   列車が現れた直後の1分だけ公式の方向が誤っていた列車（2026年10月7日 1001号）で、次の取得から方向と次の駅が正しくなる。
*   寝屋川信号場へ回送される列車で、取得・表示が止まらない。

壊れたダイヤを受け取ったときに次の取得で取り直すこと、終点に停車中は方向を更新しないことは、実データを加工したデータで確認しています。

### 5. 位置座標と遅延下限の検証

自動テストは2026年11月8日時点で550件すべて成功しています。座標から駅内・駅間を求める処理は、公式路線図の配置に基づく期待値と照合しています。地下区間と宇治線・交野線の始発駅付近、終端の番線枠、枠外の入力を含みます。

保存した実データでは、次のことを確認しています。この走査・再生は、通常の `pytest` に含まれるテストではありません。

*   **33日間の座標変換**：読み込めた列車観測のべ1,517,593件（異なる座標348個）すべてで、座標変換が例外なく動作しました。これは観測された座標を受け付けられることの確認であり、全座標の駅名が正しいことを独立に照合した結果ではありません。
*   **7日分の再生**：10月30日・11月3日〜8日の位置情報7,291件を、保存したダイヤの更新とともに時刻順に読み込ませました。壊れたJSON272件を拒否し、残る7,019件で取得処理が完了しました。11月8日は0時35分までです。
*   **位置・履歴の確認**：再生中の列車状態308,560件で、履歴・現在位置・遅延値の整合性などを確認しました。駅内・駅間の配置を照合した行では、21,454件の観測が期待する区別と一致しました。別の2件では、WDF番号の重複による現在位置と最新履歴の不一致がありました（[WDF番号の重複・再利用](#wdf番号の重複再利用)）。
*   **遅延下限の確認**：公式値が120分未満の302,859件では推定値が公式値と一致しました。「2時間以上」の5,701件ではすべて計算できました。実際の遅延との照合による精度評価とは区別します（[計算結果と実例](#2時間以上の遅延下限推定)）。

## ダイヤが乱れたとき

ダイヤが乱れているときは、ライブラリは次のように動作します。

*   **ダイヤに無い列車**
    運休・運転整理などで、位置情報にはあるのにダイヤには無い列車が走ることがあります。この列車の種別・行先・方向は公式APIの値で正しく取得できます。一方、停車駅・時刻・始発駅は分かりません。`has_dia` で判別でき、始発駅を取得しようとすると `DiaNotFoundError` になります。
*   **時刻不明の停車駅**
    運転整理された列車では、停車する駅の時刻が不明になることがあります。この場合も、停車駅として正しく扱います（時刻は `None`）。駅の発車標では、時刻不明の列車は最後に並びます。
*   **ダイヤと実際の運行のずれ**
    ダイヤに載っている列車でも、実際の停車駅や行先がダイヤと異なることがあります。種別・行先は走行中の公式の値を優先しますが、停車駅・次の停車駅はダイヤ通りの値になります。

### 運行が止まったとき

運行が止まっている間、列車の `delay_minutes` は待たされた時間だけ増え続けます。そのため、「遅延分数＋ダイヤの時刻」で求めた到着時刻は、止まっている間ずっと実際より早くなります。`delay_growing_trains()` は、遅延が経過時間とほぼ同じ速さで増えている列車を返します。止まっているかどうかの手がかりになります。

2026年10月7日〜30日（5時以降）の位置情報で、既定の `window=5分`・`ratio=0.9` で同時に当てはまった本数（`delay_growing_trains(line)` の本数）は次のとおりでした。始発駅で発車を待っている列車は、止まっていない時間帯にはほとんど当てはまらず（延べ34,798回のうち1回）、停電中は発車できずに待たされて当てはまりました。

| 路線 | 下の2回以外の最大 | 10月8日朝（交野線が止まった） | 10月30日夕方（京阪本線の停電） |
| :--- | :---: | :---: | :---: |
| 京阪本線・鴨東線 | 3本（走行約30〜60本） | 5本／59本 | 48本／50本 |
| 中之島線 | 2本 | 2本／3本 | 4本／4本 |
| 交野線 | 0本 | 5本／5本 | 2本／4本 |
| 宇治線 | 0本 | 0本 | 0本 |

*   **10月30日の停電（17時43分ごろ）**：京阪本線で当てはまる列車は、17時48分に2本、49分に5本、54分に16本と増えました。公式の遅延の表示が列車ごとに少しずつ付き始めるため、一度には増えません。
*   **10月8日朝**：交野線の列車が、7時35分から順に当てはまり、7時46分に5本すべてになりました。枚方市で90分近く動かなかった列車もあります。京阪本線にも影響が出ましたが、当てはまったのは最大5本でした。
*   **止まっていない日**：京阪本線では、数本が数分だけ遅延を増やす小さな詰まりがありました（最大3本、遅延5〜8分）。
*   **確かめられていないこと**：宇治線が止まった例はありません。京阪本線の一部の区間だけが止まった例も、はっきりしたものはありません。
*   **2時間を超えると当てはまらない**：遅延が「2時間以上」になると `delay_minutes` が120で止まるため、止まったままでも当てはまらなくなります。10月30日も、20時半以降は当てはまる列車がいなくなりました。`delay_minutes == 120` の列車がいれば、それだけで遅延分数は当てになりません。
*   **既定値の選び方**：10月25日・27日〜30日を再生して、`window` を2〜10分、`ratio` を50〜100%で比べました。`window=5分`・`ratio=0.9` は、止まっていない時間帯に全路線で同時に当てはまったのが最大1本でした。窓を4分に縮めても停電を見つける時刻は変わらず、止まっていない時間帯に当てはまる本数が増えました。窓を長くすると、見つけるのが遅くなりました。

### 2時間以上の遅延下限推定

`ActiveTrainData.estimated_delay_minutes` は、「少なくとも何分遅れているか」を推定するプロパティです。`delay_minutes < 120` なら公式値をそのまま返します。120分以上の場合は、次の候補の最大値を返します。時刻差は分単位で切り捨てます。

1. 公式値 `delay_minutes`（「2時間以上」なら120）。
2. 停車中の駅について、現在の座標を初めて観測した記録の**直前の記録時刻 − その駅の予定発車時刻**。直前の記録がない場合や予定時刻が不明な場合は、この候補を使いません。
3. **位置情報の作成時刻 `position_created_at` − 次の未到着の停車駅の予定発車時刻**。走行中は `current_or_next_stop`、停車中は現在駅の次の停車駅を使います。次の駅がない場合や予定時刻が不明な場合は、この候補を使いません。

ここで使うダイヤ時刻の元は、公式の予定発車時刻です。例えば、10:00発車予定の駅に12:30時点ではまだ到着しておらず、12:31に初めて停車を観測した場合、候補2は150分です。12:31を使った151分は、観測までの時間も含むため使いません。到着と発車の間の停車時間は分からないため、厳密な予定到着時刻との比較ではありません。

ダイヤがない列車や終着後の回送など、`current_or_next_stop` 自体が不明な場合は、公式値をそのまま返します。その他の候補を計算できない場合も、公式値が残ります。`delay_minutes`、`history` 内の遅延分数、`delay_growth_rate()` の計算は、この推定値に置き換わりません。

推定は最後に取得できた位置情報の時点の値です。取得失敗中や公式データの更新が止まっている間に、実時計だけで増えることはありません。現在のダイヤと実際の停車駅・経路が一致し、座標の変化がその駅への到着を表すことが前提です。観測開始前や取得間隔中の正確な到着時刻、今後の運転再開時刻や遅れの回復は分かりません。

33日間の保存データで「2時間以上」があったのは10月30日だけでした。同日を再生した5,701件の観測のうち、5,355件で120分を超える下限を返し、最大は170分でした。次の停車駅が不明な78件では、公式値の120分を返しました。推定値を読み出しても、現在値・履歴の公式遅延値が変わらないことも確認しました。

例えば、10月30日の1806号（WDF番号974）は、神宮丸太町の予定到着が20:09、到着前の最後の観測が22:59:23、最初の駅上観測が23:00:23でした。走行中の観測と最初の駅上観測の両方で、下限は170分でした。最初の駅上観測を到着時刻として使った171分にはなっていません。正確な到着時刻は観測の間にあるため、この例から実際の遅延を170分と確定することはできません。

この値は実際の遅延分数や将来の到着時刻の予測ではありません。「少なくとも150分遅れ」のように表示し、予定時刻に加算して確定的な到着予測として扱わないでください。再生で計算結果は確認しましたが、実際の遅延との照合による精度検証は未実施です。

## 公式APIが異常なデータを返したとき

公式APIは、次のようなデータを返すことがあります。いずれも実際に確認したものです。

*   **壊れたJSON**
    末尾にNULが付いたJSONや、途中で切れたJSONが返ることがあります。2026年10月7日〜30日に `snapshot_dir` で保存した位置情報26,123件のうち741件（約2.8%）が壊れていました。毎日17〜48回、始発から終電までどの時間帯にも起き、1分に1回取得すると1時間に1〜2回は当たります。壊れ方は末尾のNULが390件、途中で切れたものが349件、その他が2件です。ダイヤは473件のうち、壊れていたものはありません。`fetch_pos()` は `KeihanAPIError`（`ValueError` のサブクラス）を送出します。位置情報が壊れていた場合、列車の状態は前回のまま変わりません。ダイヤが壊れていた場合は、位置情報だけ更新され、ダイヤは次の取得で取り直します。
*   **長時間の停止**
    公式サイトが止まり、APIが長時間 `502 Bad Gateway` を返し続けることがあります。2026年10月21日20時45分ごろから22日18時50分ごろまでの約22時間は、PHPの脆弱性への対策で京阪のホームページ全体が休止していました（[ABCニュース](https://news.yahoo.co.jp/articles/fcd8505db698f0e37fc37c9b459a47ab5355c164)）。この間、`fetch_pos()` は `httpx.HTTPStatusError` を送出し、列車の状態は最後に取得できたときのまま残ります。`last_fetch_pos_datetime` は失敗した取得でも更新されるため、データの古さは `position_created_at`（手元の位置情報の作成時刻）で判断してください（[表示する側でやること](#表示する側でやること)）。
*   **行先なし**
    全列車の行先が「00」で返ることがあります（2026年10月7日 23時台）。行先はダイヤの終着駅で補います。走行中に「00」になった場合は、直前の行先を保ちます。
*   **方向の一時的な誤り**
    列車が現れた直後の1分だけ、公式の方向が誤ることがあります。次の取得で公式の値に合わせて直ります。最初の1分間は誤ったままです。

### 運行中に変わる値の集計

2026年10月7日〜30日に `snapshot_dir` で保存した位置情報のうち、読み込めた25,382件を集計しました。同じWDF番号が続けて現れる区間（1運行）は23,953本です。

ここでの「1運行」はWDF番号に基づく集計単位です。同じ営業日に同じWDF番号が複数の列車番号で現れたのは、24日間で23,940件（WDF番号と営業日の組み合わせ）のうち、10月30日のWDF番号32768の1件だけでした。大半は実際の運行と一対一に対応しますが、この1件では対応しません。

*   **列車番号**：ライブラリはWDF番号ごとに最初に観測した列車番号を保持し、その後の番号の変化は追いません。WDF番号の再利用は上の1件だけですが、その例では同じWDF番号に1751号・1860号・1753号・2260号が混在するため、番号の変化から同一運行の番号変更を判定できません（[WDF番号の重複・再利用](#wdf番号の重複再利用)）。
*   **方向**：運行中に482回変わり、すべて上り→下りでした。
    *   268回は、現れてから3分以内です。上の「方向の一時的な誤り」で、下りの運行12,124本のうち約2%にあたります。
    *   残りの214回は、運行の終わり（終点に停車中）です。公式の方向が次の運行の向きに変わるためで、ライブラリは終点に停車中は方向を更新しません。
*   **行先**：運行中に710回変わりました。うち701回は「00」（行先なし）と実際の駅の行き来で、別の駅に変わったのは9回（運転整理）です。

## 京阪バスの接近情報

`get_khbus_info()` は、京阪グループ「BUS NAVI」の接近情報をほぼそのまま返す薄いラッパーです。サイネージなどでの表示を想定しています。

*   **値はすべて公式の値そのまま**です。接近順位・系統・行先・経由・状態（「まもなく到着」など）・時刻（「17:30 到着予定」など）は、BUS NAVI がすでに計算した表示用の値で、電車のようなライブラリによる推定は入りません。時刻は文字列のままなので、そのまま表示できます。並べ替えには接近順位 `order` を使えます。
*   **壊れた応答は `KeihanAPIError` になります**。壊れたJSONや、`busstateprms` の区切りの数が想定（12個）と違う応答は、電車と同じ `KeihanAPIError` を送出します。区切りが多すぎる場合も、項目がずれて誤った表示になるのを防ぐため例外にします。通信の失敗は `httpx.HTTPError` です。サイネージでは、この2つを捕まえて前回の表示を保つと、APIの形式が変わっても止まりません。
*   **同じバス停は30秒間キャッシュします**。30秒以内に同じバス停・のりばを取得すると、前回の結果を返します。取得に失敗したときはキャッシュしないので、次の呼び出しで取り直します。
*   **指定した便の発着時刻表も取得できます**。各便の `dgmpl` は、HTML 内の `bus_key` から公式ページの「終点までの発着時刻表」と同じ方法で作ります。`fetch_diagram(dgmpl)` を呼ぶと、停留所ごとの着時刻・発時刻を運行順に返します。始発の着時刻や終点の発時刻など、記載がない値は `None`、公式が `△` を付けた推定時刻はフラグで区別します。時刻は公式ページの値で、遅延を加算した到着予測ではありません。同じ `dgmpl` は30秒間キャッシュします。

### 分かっている限界

*   **存在しないバス停を区別できない**：存在しないバス停名を指定しても、バスが来ていないときと同じ空の応答（`errorcode` は 0）が返ります（2026年10月26日に確認）。バス停名の誤りに気付けないため、設置時にバスの走る時間帯で表示を確認してください。
*   **実データの検証範囲が限られる**：2026年11月7日の同志社香里・1番のりばの接近情報1応答（7件）と、寝屋川市駅［東口］〜京阪香里園の発着時刻表1便（17停留所）を `tests/fixtures/bus/` に保存しています。便ごとの `dgmpl`、停留所の順序、同じ停留所を2回通る場合、到着と発車が異なる時刻、始発・終点の欠けた時刻を自動テストします。ほかの停留所・便は実データで検証していません。推定時刻や24時以降の表記、壊れた応答は、組み立てたデータでテストしています。
*   **項目の意味が推測のもの**：`stop_id`（停留所ID）と `platform_index`（のりば）は推測です。表示に使う系統・行先・経由・状態・時刻は、意味がはっきりしています。

## v3 の到着予測の確認

`estimate_arrival(train, station, *, now, policy=EtaPolicy())` は通信せず、渡されたタイムゾーン付きの now で計算します。
`KHTracker.eta()`・`KHTrackerSync.eta()` は現在時刻（JST）を渡します。
ダイヤなし・停車しない駅・時刻不明・通過済み・位置関係不明は、例外ではなく time=None と専用の理由です。

既定の係数と閾値は signage に合わせました。公式の遅れが120分以上、遅れが増加中、始発駅以外で15分超停滞、
前詰まり、予測範囲外の順に時刻を伏せます。前詰まりは本線・中之島線を走る列車と、京橋〜出町柳の対象駅で判定し、
120分以上の遅れだけでは前詰まりの原因にはしません。始発駅の発車待ちは長時間停滞から除きますが、遅れ増加からは除きません。
係数や閾値は `EtaPolicy` で変更できます。

signage の関数を直接呼んだ22,494組（平日・土休日を含む全走行列車×全停車駅）の結果を新規fixtureに保存しました。
22,024組が一致し、470組は signage が過去時刻の行を一覧から除外することによる差でした。この差を変えずに全件記録しています。
元の境界値テストも移しました。[比較手順・一覧](ETA_SIGNAGE.md) に参照コミットと入力・出力があります。
これは実装の照合であり、実際の到着時刻に対する精度の検証ではありません。

`watch(on_error="continue")` は失敗回を yield しないため、失敗が続いた場合に画面を消す処理は別のタイマーで古さを確認してください。
予測関数は情報の古さ、一覧の件数制限、最低残り時間、未走行の後続列車の表示制御を担当しません。

## 表示する側でやること

ライブラリは公式値と予測結果を返します。v3 の `eta()` は予測を伏せる理由も返しますが、画面全体を消すか、代わりに何を表示するかは使う側で判断してください。

*   **データの古さ**：取得に失敗している間、列車の状態は最後に取得できたときのまま残ります。そのまま表示し続けると、古い位置や遅延を最新のように見せてしまいます。`position_created_at`（手元の位置情報の作成時刻）は取得に失敗しても進まないため、現在時刻との差でデータの古さが分かります。壊れたJSONが返り続けたときや、APIが止まったとき（[公式APIが異常なデータを返したとき](#公式apiが異常なデータを返したとき)）も同じです。公式の位置情報は1分ごとに作られるため、1分ごとに取得していれば差は通常2分以内です。差が数分を超えたら、「情報が古い」と表示するか、列車の表示を消してください。
*   **予測不能時の表示**：運行が止まっている間、「遅延分数＋ダイヤの時刻」で求めた到着時刻は実際より早くなります（[運行が止まったとき](#運行が止まったとき)）。`eta()` の time が None なら reason を見て、位置や停滞時間に切り替えられます。`estimated_delay_minutes` は遅れの下限であり、到着予測には加算しません。

## 分かっている限界

### 停車駅だけでは区別できない種別

走行前の列車の種別は停車駅から推定するため、停車駅がまったく同じ種別は区別できません。走行中になれば、公式の値で正しく表示されます。

| 区別できない組み合わせ | 推定結果 |
| :--- | :--- |
| ライナーと特急 | 特急 |
| 樟葉始発のライナーと通勤快急（樟葉始発ライナーは香里園・寝屋川市にも停車するため） | 通勤快急 |
| 準急・通勤準急と普通（萱島以北だけを走る区間など） | 普通 |
| 快速急行と通勤快急（守口市を通らない区間） | 快速急行 |

### WDF番号の重複・再利用

ライブラリはWDF番号（`wdf`）をキーに列車を管理し、一度消えて再び現れた同じWDF番号の列車には、それまでの履歴を引き継ぎます。公式データには同じ営業日の中で同じWDF番号が重複・再利用される例があり、その場合は列車属性や履歴を正しく区別できません。

10月7日〜11月8日の位置情報を走査したところ、同一応答内のWDF番号の重複は10月30日の次の2応答にありました。時刻は位置情報の `fileCreatedTime` です。

| 時刻 | 1860号のWDF番号 | 1751号のWDF番号 |
| :--- | :--- | :--- |
| 19:54:25・19:55:26 | 32768 | 32768 |
| 19:56:26 | 3068 | 32768 |

重複した2応答を読み込むと、列車番号は1751号、現在位置は1860号の座標 `(3, 118)`、最新履歴は1751号の座標 `(3, 37)` になります。また同日の後の時刻にも、WDF番号32768は1753号・2260号として掲載されており、こうした観測の履歴が同じWDF番号のもとに連結されます。

WDF番号32768の意味や再利用の規則は未確認です。同じWDF番号という理由で同じ運行と断定することはできません。既知の重複・再利用の事例はこの1件のみで、ライブラリがどう扱うべきかを判断するのに十分なデータがないため、ライブラリは同じWDF番号の観測を分離せず、一つの履歴として引き継ぎます。そのため、保持された履歴全体が同一運行に属する保証はありません。

### 公式データにない情報・確認できていないこと

*   **非公式API**：仕様が予告なく変わる可能性があります。テストでは、仕様変更の兆候（駅番号の形式など）を検知できるようにしています。
*   **駅番号の3桁目の意味**：0が通過、1・2が停車であることはデータから確認しています。ただし、1と2の違い（時刻が載る主要駅か）は推測です。
*   **臨時の停車**：京都競馬場の開催日などに、急行・快速急行が淀に臨時停車することは確認しています。ただ、すべての臨時停車を網羅しているわけではありません。
*   **案内図にない臨時列車**：たとえば、2025年4月に運行された中之島線に乗り入れる臨時特急は、案内図の停車パターンに当てはまりません。種別の推定は「特急」になります。
*   **未検証の種別**：深夜急行・通勤急行は、検証に使ったデータに含まれていません。
*   **寝屋川信号場への回送**：寝屋川市止まりの一部は、着いたあと同じ列車のまま寝屋川信号場（ダイヤ上の駅番号99）へ向かいます。寝屋川信号場は駅として扱わないため、この間は次の停車駅が `None` になります。公式の行先は寝屋川市のままです。
*   **ダイヤ切替前の早朝**：始発前の4時半ごろには、その日の列車が位置情報に現れますが、公式のダイヤはまだ前の日のもののことがあります。平日ダイヤと土休日ダイヤが切り替わる朝（土曜と月曜）は、同じWDF番号が前の日の別の列車を指すため、前の日のダイヤのままだと停車駅・次の停車駅・種別の推定が誤る可能性があります。走行中の列車の種別・行先・方向は公式の値です。
    ライブラリは、営業日が4時に変わってから、走行中の列車の公式の行先とダイヤの終着駅が1本も食い違わなくなるまで、取得のたびにダイヤを取り直します（安全装置として5時30分まで）。切り替わるまでの間は、前の日のダイヤのままです。保存データの再生では、次の動作を確認しています。
    *   平日から平日に変わる朝は、最初の列車が現れた4時32分に行先の一致を確かめ、ダイヤの取得は1回でした。
    *   土曜（10月10日）と月曜（10月19日・26日）の朝は、前の日のダイヤでは行先が一致せず、取り直しを続け、5時1分に保存されていた新しいダイヤで一致しました。この3日のダイヤ保存間隔は1時間のため、5時1分は新しいダイヤが公開された時刻ではなく、取得できた時刻です。
    *   10月31日（土）の朝は、3時31分に取ったダイヤが前日のもので、最初の列車が現れた4時32分の取得で土休日のダイヤを確認できました。取得は1回でした。

    公式のダイヤのファイルは、夜中から朝にかけて何度も作り直されています（ファイルの `fileCreatedTime` から分かります）。毎朝のように、4時30分〜4時47分ごろと4時58分〜5時ちょうどごろに作られています。10月31日は、1時33分に作られたダイヤは前の日（平日）のもので、4時30分49秒に作られたダイヤが土休日のものでした。**公式のダイヤが切り替わる時刻は、まだこの1日分しか分かっていません**。それより前の切り替わる朝は、ダイヤを1時間に1回しか取っていなかったため、4時30分ごろに作られたダイヤが取れておらず、そのときに切り替わったかは分かりません。
*   **走らない臨時列車**：公式のダイヤには、その日に走らない臨時列車も載っています。2026年10月の土休日（10日・11日・12日・17日・18日・24日・25日）のダイヤには、臨時列車が毎回18〜22本載っていましたが、実際に走ったのは0〜10本でした。毎週載っているのに一度も走らなかった列車もあります。走るかどうかはダイヤからは分からないため、ライブラリは臨時列車を、位置情報に現れるまで登録しません。臨時列車は、走り出すまで発車標（`upcoming_trains`）に出ません。
*   **運休**：公式のダイヤからは、運休になった列車が消えません。そのため、走っていない列車がこれから走るのか、運休になったのかは分かりません。2026年10月30日の京阪本線の停電（17時43分〜）では、17時43分〜22時44分に終着する予定だった列車のうち、74本は一度も位置情報に現れませんでした。また、61本は終着の予定時刻を過ぎてから初めて現れました。`upcoming_trains` は、こうした列車を予定時刻を過ぎても含み続けます。
*   **途中で消える列車**：同じ日の停電では、止まったまま位置情報から消えて、後でまた現れた列車がありました（908は18時14分〜19時44分、1108は21時10分〜21時53分）。消えている間は `TrainData` に戻り、`was_active` は `True` のため、`upcoming_trains` には出ません。また現れると `ActiveTrainData` に戻り、`history` は続きから加わります。
