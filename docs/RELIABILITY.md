# keihan_tracker の信頼性

このドキュメントでは、keihan_tracker が返す値を**どこまで信頼してよいか**と、その**根拠となる検証**について説明します。

keihan_tracker は京阪電車の非公式APIラッパーです。京阪が公開している仕様書はなく、APIの意味はデータから読み解いています。そのため「すべて正確」とは言えませんが、**どの値が公式データそのままで、どの値が推定なのか**を区別し、推定の部分は実データで検証しています。

> 検証時点：2026年10月26日（バージョン 2.5.0）

---

## まとめ

*   **走行中の列車の種別・行先・方向・臨時かどうか・遅延は、公式APIの値そのまま**です。ライブラリによる推定は入りません。
*   **これから走る列車の種別は、停車駅からの推定**です。2022年11月〜2026年6月の過去のダイヤ26日分（のべ約3万本）で検証し、走行中の列車のべ1090本では、推定した種別が公式APIの種別と**すべて一致**しました。2026年10月7日〜25日の19日間に走った列車18,237本では**99.75%が一致**し、食い違いはすべて原因が分かっています。
*   **ダイヤが乱れているときも落ちません**。ダイヤに無い列車や、時刻不明の停車駅を含むデータでも動作することを、実際のダイヤ乱れのデータで確認しています。
*   **公式APIが異常なデータを返しても、状態は壊れません**。壊れたJSONは `KeihanAPIError` になり、列車の状態は前回のまま残ります。行先なしのデータや、一時的に誤った方向も、実際に返ってきたデータで動作を確認しています（[公式APIが異常なデータを返したとき](#公式apiが異常なデータを返したとき)）。
*   **京阪バスの接近情報は、公式の値をほぼそのまま返します**。壊れた応答は電車と同じ `KeihanAPIError` になります。ただし実データでのテストはなく、存在しないバス停名を区別できません（[京阪バスの接近情報](#京阪バスの接近情報)）。
*   **関西エリア全体の運行情報（Yahoo!路線情報・駅すぱあと）は非推奨で、検証していません**（[運行情報](#運行情報yahoo路線情報駅すぱあと)）。
*   一方で、停車駅だけでは区別できない種別の組み合わせ（ライナーと特急など）や、ダイヤ乱れ時にダイヤと実際の運行がずれることなど、**原理的に避けられない限界**があります（[分かっている限界](#分かっている限界)）。

## 値ごとの出どころと信頼度

keihan_tracker の値は、次の3種類のどれかから来ています。

*   **位置情報**：公式の `trainPositionList.json`。走行中の列車のリアルタイム情報
*   **ダイヤ**：公式の `startTimeList.json`。その日の全列車の停車駅・時刻
*   **推定**：上の2つから、ライブラリが独自に計算した値

| 値 | 出どころ | 信頼度 | 補足 |
| :--- | :--- | :---: | :--- |
| 種別（走行中） | 位置情報 | ◎ | 公式の値そのまま |
| 行先（走行中） | 位置情報 | ◎ | 公式の値そのまま。行先なし（00）のときはダイヤの終着駅で補い、ダイヤも無ければ `None` |
| 方向（走行中） | 位置情報 | ○ | 公式の値そのまま。ただし公式の値が、列車が現れた直後の1分だけ誤ることがある（下りの運行の約2%。次の取得で直る）。終点に停車中は更新しない |
| 臨時列車かどうか `is_special` | 位置情報 | ◎ | 公式の種別表示に「臨時」が付いているか |
| 遅延 `delay_minutes` | 位置情報 | ◎ | 公式の値そのまま |
| 列車番号・両数 | 位置情報 | ◎ | 公式の値そのまま |
| 停車駅・時刻 `stop_stations` | ダイヤ | ○ | ダイヤ通りの値。ダイヤ乱れ時は実際と異なる場合あり |
| プレミアムカー・編成番号 | ダイヤ | ○ | ダイヤ上の値 |
| 次の停車駅 `next_stop_station` | 位置情報＋ダイヤ | ○ | 現在位置とダイヤの停車駅から計算 |
| 駅の位置にいるか `is_at_station` | 位置情報から推定 | ○ | 路線図上の座標から判定。通過中も含む |
| 停車中かどうか `is_stopping` | 位置情報＋ダイヤ | ○ | 駅の位置にいて、その駅が次の停車駅なら停車中。通過駅の位置なら `False`。次の停車駅が分からない（ダイヤに無い列車など）ときは `None` |
| 同じ位置に留まっている時間 `staying_time` | 位置情報から計算 | ○ | 座標が変わらない時間。駅でも駅間でも増える。位置情報の作成時刻で測るため、APIが止まっている間は増えない。座標が粗いため走行中でも数分は増えることがある |
| 種別（走行前・走行後） | 停車駅から推定 | ○ | 後述の検証あり。一部区別できない組み合わせあり |
| 方向（走行前） | 始発・終着から推定 | ○ | 走行中の列車で公式の値と照合済み |
| 運行状態 `status` の `"scheduled"` / `"completed"` | 時刻から推定 | △ | ダイヤ上の時刻との比較のみ。遅延は考慮しない |

なお、走行中だった列車が運行を終えると、走行中に取得した種別・方向・行先・路線は引き継がれます。推定値に置き換わることはありません。

## 検証の内容

### 1. 実データを使った自動テスト

`tests/` に、実際のAPIレスポンスを保存したデータを使った自動テストがあります。GitHub Actions で、Python 3.10〜3.13 の各バージョンについて、push のたびに実行しています。

テストには、次の実データを使っています。

*   2026年10月6日（火）21時台の位置情報・ダイヤ（平日ダイヤ。走行中の列車を含む）
*   Wayback Machine から保存した2022年11月〜2026年6月の26日分・28スナップショットのダイヤ（平日・土休日を含む）。うち25件は位置情報も保存
*   2026年10月7日〜10日に `snapshot_dir` で保存した、公式APIの異常な位置情報9件（`tests/fixtures/irregular/`）。ダイヤは保存していないため、10月6日の平日ダイヤと組み合わせています

通常の `python -m pytest tests -q` で、上記の全データをネットワークに接続せずに検証します。行先と方向の整合性は現在の平日データと全28アーカイブが対象で、出町柳行きは上り（京都方面）、淀屋橋・中之島行きは下り（大阪方面）であることを確認します。ダイヤがある走行中の列車では、推定方向と公式の方向も照合します。ダイヤに無い列車は推定方向を求められないため、行先と公式の方向の整合性を検証します。

アーカイブの元データは `tests/fixtures/wayback/` に圧縮して保存し、`manifest.json` に取得元URL・取得日時・列車数・元データのSHA-256を記録しています。26日分のダイヤは延べ29,618列車、対応する位置情報は延べ1,097列車です。元データの欠落・改変も通常のテストで検知します。

### 2. 停車駅からの種別推定の検証

走行前の列車には、公式データに種別が含まれません。そのため、停車駅のパターンから種別を推定しています。この推定を、次の4つの方法で検証しています。

**(1) 停車パターンの網羅テスト**

テスト用データのダイヤに含まれる停車パターンを、すべて列挙してテストしています。平日ダイヤの99通りと、過去のダイヤにだけある23通り、`snapshot_dir` で保存したダイヤで見つかった1通りが対象です。どのパターンが、どの種別と推定されるべきかを1つずつ確認しています。

**(2) 公式の停車駅案内図との照合**

京阪公式の停車駅案内図を、テストの中に書き写しています。推定した種別が案内図と矛盾しないことを、全列車について確認しています。

**(3) 過去のダイヤと公式の種別との照合**

Wayback Machine（インターネットアーカイブ）に保存されていた過去のダイヤ26日分（スナップショット28件）を使って検証しました。期間は2022年11月〜2026年6月で、のべ約3万本の列車を含みます。

*   走行中だった列車のべ1090本について、停車駅から推定した種別と公式APIの種別を比べました。結果は、**食い違い0本**です。普通・区間急行・準急・通勤準急・急行・快速急行・通勤快急・特急・快速特急 洛楽・ライナーの、すべての種別を含みます。ライナーは特急と推定されるため、特急として扱っています。
*   土休日ダイヤも含めて、快速特急 洛楽の本数が実際の運行（平日2本・土休日8本）と一致することも確認しています。

**(4) 19日間に走った列車と公式の種別との照合**

2026年10月7日〜25日に `snapshot_dir` で保存した位置情報とダイヤ（毎日保存）を使って検証しました。運行（同じ `wdfBlockNo` が続けて現れる区間）18,243本のうち、ダイヤのある18,237本について、運行が現れた時点のダイヤの停車駅から推定した種別を、公式APIの種別と比べました。平日・土休日の両方と、臨時列車を含みます。

*   **18,192本（99.75%）が一致**しました。ライナー149本のうち112本は特急と推定されるため、特急として扱っています。
*   食い違いは45本で、すべて原因が分かっています。
    *   **37本**は樟葉始発のライナーで、通勤快急と推定されました。停車駅が通勤快急と同じため、区別できません（[停車駅だけでは区別できない種別](#停車駅だけでは区別できない種別)）。
    *   **8本**は、土曜（10月10日・17日・24日）と月曜（10月19日）の4時半ごろに現れた列車です。この時間はまだ前の日のダイヤしかなく、前の日のダイヤで推定したためです。その日の5時以降のダイヤで推定すると、8本とも一致しました（[ダイヤ切替前の早朝](#公式データにない情報確認できていないこと)）。
*   臨時列車31本は、すべて一致しました。10月17日の淀川花火大会の臨時列車4本や、週末に淀を発着する臨時列車を含みます。この検証で、香里園発淀行きの臨時普通を特急と推定する不具合が見つかり、修正しました。
*   ダイヤに無い列車は6本で、すべて10月19日の1時台に走ったものです。

### 3. ダイヤ乱れ時のデータでの動作確認

過去のデータには、ダイヤ乱れのときのものが含まれていました。たとえば、2026年4月28日の淀屋橋〜枚方市間の停電や、2025年3月21日の運転整理です。これらのデータで、次のことを確認しています。

*   位置情報とダイヤがそろったスナップショット25件すべてで、列車の表示・駅の発車標・列車の検索が例外を出さずに動作する。
*   ダイヤに無い列車（のべ7本）は、公式の種別・行先などを正しく保持する。
*   時刻不明の停車駅を含む列車は、停車駅と種別を正しく扱う。

### 4. 公式APIの異常なデータでの動作確認

`tests/fixtures/irregular/` の実データで、次のことを確認しています。

*   末尾にNULが付いたJSON・途中で切れたJSONで `KeihanAPIError` になり、列車の状態が変わらない。次の取得で正常なデータが来れば、続きから動作する。
*   全列車の行先が「00」（行先なし）のデータで、取得が止まらない。
*   列車が現れた直後の1分だけ公式の方向が誤っていた列車（2026年10月7日 1001号）で、次の取得から方向と次の駅が正しくなる。
*   寝屋川信号場へ回送される列車で、取得・表示が止まらない。

壊れたダイヤを受け取ったときに次の取得で取り直すこと、終点に停車中は方向を更新しないことは、実データを加工したデータで確認しています。

### 5. 検証で見つかり、修正した問題

検証で次の問題が見つかり、修正済みです。

*   **寝屋川市発・出町柳行きの快速急行を、特急と推定していた**（2.2.3 まで）
*   **ダイヤ乱れ時に、時刻不明の停車駅を通過駅として扱っていた**（2.2.3 まで）。停車駅が抜け落ちて、種別を誤って推定することがありました。
*   **ダイヤに無い列車で例外が発生していた**（2.2.3 まで）。運行を終えたあとに列車を行先で検索すると、検索全体が失敗していました。
*   **走行中の列車の方向・行先を更新していなかった**（2.3.0 まで）。列車が現れた直後の1分だけ公式の方向が誤っていると、その運行の間ずっと逆向きのままで、次の駅も列車の後ろの駅になっていました。
*   **行先なし（00）のデータで取得が止まっていた**（2.3.0 まで）。23時台に全列車の行先が「00」で返ったとき、全列車の更新が止まっていました。
*   **壊れたダイヤを受け取ると、1時間取り直さなかった**（2.3.0 まで）。日付が変わった直後に起きると、前日のダイヤのまま動いていました。
*   **通過駅の位置にいる列車を、停車中としていた**（2.4.1 まで）。`is_stopping` は座標だけで判定しており、通過列車が駅の位置に乗った瞬間も停車中になっていました。
*   **駅間での足止めを検出できなかった**（2.4.1 まで）。停車時間 `stopping_time` は駅に停車中のときだけ数えていたため、駅間で止まった列車は0のままでした。同じ位置に留まっている時間 `staying_time` に置き換えました。
*   **4時半〜5時に現れた列車の時刻が、1日前になっていた**（2.4.1 まで）。営業日が5時に変わっていたため、始発前に現れた列車のダイヤの時刻を前の日の日付で組み立てていました。営業日が変わる時刻を、列車が走っていない4時にしました。
*   **香里園発淀行きの臨時普通を、特急と推定していた**（2.4.1 まで）。京橋も鳥羽街道も通らない列車を、出町柳〜三条のような京都側の短い列車とみなしていたためです。始発から終着までの駅にすべて停車する列車は、普通と推定するようにしました。
*   **バスの応答の形式が変わると、`IndexError` がそのまま送出されていた**（2.4.1 まで）。区切りが多すぎる場合は、黙って項目がずれていました。

## ダイヤが乱れたとき

ダイヤが乱れているときは、ライブラリは次のように動作します。

*   **ダイヤに無い列車**
    運休・運転整理などで、位置情報にはあるのにダイヤには無い列車が走ることがあります。この列車の種別・行先・方向は公式APIの値で正しく取得できます。一方、停車駅・時刻・始発駅は分かりません。`has_dia` で判別でき、始発駅を取得しようとすると `DiaNotFoundError` になります。
*   **時刻不明の停車駅**
    運転整理された列車では、停車する駅の時刻が不明になることがあります。この場合も、停車駅として正しく扱います（時刻は `None`）。駅の発車標では、時刻不明の列車は最後に並びます。
*   **ダイヤと実際の運行のずれ**
    ダイヤに載っている列車でも、実際の停車駅や行先がダイヤと異なることがあります。種別・行先は走行中の公式の値を優先しますが、停車駅・次の停車駅はダイヤ通りの値になります。

## 公式APIが異常なデータを返したとき

公式APIは、次のようなデータを返すことがあります。いずれも実際に確認したものです。

*   **壊れたJSON**
    末尾にNULが付いたJSONや、途中で切れたJSONが返ることがあります。2026年10月7日〜25日に `snapshot_dir` で保存した位置情報20,094件のうち571件（約2.8%）が壊れていました。毎日17〜48回、始発から終電までどの時間帯にも起き、1分に1回取得すると1時間に1〜2回は当たります。壊れ方は末尾のNULが約半分、残りはほぼ途中で切れたものです。`fetch_pos()` は `KeihanAPIError`（`ValueError` のサブクラス）を送出します。位置情報が壊れていた場合、列車の状態は前回のまま変わりません。ダイヤが壊れていた場合は、位置情報だけ更新され、ダイヤは次の取得で取り直します。
*   **長時間の停止**
    公式サイトが止まり、APIが長時間 `502 Bad Gateway` を返し続けることがあります。2026年10月21日20時45分ごろから22日18時50分ごろまでの約22時間は、PHPの脆弱性への対策で京阪のホームページ全体が休止していました（[ABCニュース](https://news.yahoo.co.jp/articles/fcd8505db698f0e37fc37c9b459a47ab5355c164)）。この間、`fetch_pos()` は `httpx.HTTPStatusError` を送出し、列車の状態は最後に取得できたときのまま残ります。`last_fetch_pos_datetime` は失敗した取得でも更新されるため、データの古さは呼び出し側で判断してください。
*   **行先なし**
    全列車の行先が「00」で返ることがあります（2026年10月7日 23時台）。行先はダイヤの終着駅で補います。走行中に「00」になった場合は、直前の行先を保ちます。
*   **方向の一時的な誤り**
    列車が現れた直後の1分だけ、公式の方向が誤ることがあります。次の取得で公式の値に合わせて直ります。最初の1分間は誤ったままです。

### 運行中に変わる値の集計

2026年10月7日〜25日に `snapshot_dir` で保存した位置情報のうち、読み込めた19,523件を集計しました。同じ `wdfBlockNo` が続けて現れる区間（1運行）は18,243本です。

*   **列車番号**：運行中に変わったのは0件です。`wdfBlockNo` は1運行に1つで、折り返しても引き継がれません。
*   **方向**：運行中に366回変わり、すべて上り→下りでした。
    *   199回は、現れてから3分以内です。上の「方向の一時的な誤り」で、下りの運行9,382本のうち約2%にあたります。
    *   残りの167回は、運行の終わり（終点に停車中）です。公式の方向が次の運行の向きに変わるためで、ライブラリは終点に停車中は方向を更新しません。
*   **行先**：運行中に620回変わりました。うち613回は「00」（行先なし）と実際の駅の行き来で、別の駅に変わったのは7回（運転整理）です。

## 京阪バスの接近情報

`get_khbus_info()` は、京阪グループ「BUS NAVI」の接近情報をほぼそのまま返す薄いラッパーです。サイネージなどでの表示を想定しています。

*   **値はすべて公式の値そのまま**です。接近順位・系統・行先・経由・状態（「まもなく到着」など）・時刻（「17:30 到着予定」など）は、BUS NAVI がすでに計算した表示用の値で、電車のようなライブラリによる推定は入りません。時刻は文字列のままなので、そのまま表示できます。並べ替えには接近順位 `order` を使えます。
*   **壊れた応答は `KeihanAPIError` になります**。壊れたJSONや、`busstateprms` の区切りの数が想定（12個）と違う応答は、電車と同じ `KeihanAPIError` を送出します。区切りが多すぎる場合も、項目がずれて誤った表示になるのを防ぐため例外にします。通信の失敗は `httpx.HTTPError` です。サイネージでは、この2つを捕まえて前回の表示を保つと、APIの形式が変わっても止まりません。
*   **同じバス停は30秒間キャッシュします**。30秒以内に同じバス停・のりばを取得すると、前回の結果を返します。取得に失敗したときはキャッシュしないので、次の呼び出しで取り直します。

### 分かっている限界

*   **存在しないバス停を区別できない**：存在しないバス停名を指定しても、バスが来ていないときと同じ空の応答（`errorcode` は 0）が返ります（2026年10月26日に確認）。バス停名の誤りに気付けないため、設置時にバスの走る時間帯で表示を確認してください。
*   **実データでのテストがない**：テストは、パーサーが前提にしている形式で組み立てた応答を使っています。実際の応答は保存していません。
*   **項目の意味が推測のもの**：`stop_id`（停留所ID）と `platform_index`（のりば）は推測です。表示に使う系統・行先・経由・状態・時刻は、意味がはっきりしています。

## 運行情報（Yahoo!路線情報・駅すぱあと）

`get_yahoo_delay()` と `get_ekispert_delay()` は**非推奨**で、将来のバージョンで削除する可能性があります。呼び出すと `DeprecationWarning` を出します。

*   **京阪のデータではありません**。関西エリア全体の運行情報で、このライブラリの検証の対象外です。
*   **Yahoo!路線情報**：ページのスクレイピングです。Yahoo!路線情報は運行情報の二次利用を禁止しています。ページの構成が変わると、`IndexError` などがそのまま送出されます。
*   **駅すぱあと**：有料契約が必要なAPIで、動作を確認できていません。

## 分かっている限界

### 停車駅だけでは区別できない種別

走行前の列車の種別は停車駅から推定するため、停車駅がまったく同じ種別は区別できません。走行中になれば、公式の値で正しく表示されます。

| 区別できない組み合わせ | 推定結果 |
| :--- | :--- |
| ライナーと特急 | 特急 |
| 樟葉始発のライナーと通勤快急（樟葉始発ライナーは香里園・寝屋川市にも停車するため） | 通勤快急 |
| 準急・通勤準急と普通（萱島以北だけを走る区間など） | 普通 |
| 快速急行と通勤快急（守口市を通らない区間） | 快速急行 |

### 公式データにない情報・確認できていないこと

*   **非公式API**：仕様が予告なく変わる可能性があります。テストでは、仕様変更の兆候（駅番号の形式など）を検知できるようにしています。
*   **駅番号の3桁目の意味**：0が通過、1・2が停車であることはデータから確認しています。ただし、1と2の違い（時刻が載る主要駅か）は推測です。
*   **臨時の停車**：京都競馬場の開催日などに、急行・快速急行が淀に臨時停車することは確認しています。ただ、すべての臨時停車を網羅しているわけではありません。
*   **案内図にない臨時列車**：たとえば、2025年4月に運行された中之島線に乗り入れる臨時特急は、案内図の停車パターンに当てはまりません。種別の推定は「特急」になります。
*   **未検証の種別**：深夜急行・通勤急行は、検証に使ったデータに含まれていません。
*   **寝屋川信号場への回送**：寝屋川市止まりの一部は、着いたあと同じ列車のまま寝屋川信号場（ダイヤ上の駅番号99）へ向かいます。寝屋川信号場は駅として扱わないため、この間は次の停車駅が `None` になります。公式の行先は寝屋川市のままです。
*   **ダイヤ切替前の早朝**：始発前の4時半ごろには、その日の列車が位置情報に現れますが、公式のダイヤはまだ前の日のもののことがあります。平日ダイヤと土休日ダイヤが切り替わる朝（土曜と月曜）は、同じ `wdfBlockNo` が前の日の別の列車を指すため、前の日のダイヤのままだと停車駅・次の停車駅・種別の推定が誤ります（10月7日〜25日の照合で8本）。走行中の列車の種別・行先・方向は公式の値なので、影響を受けません。
    2.5.0 からは、営業日が4時に変わり、そこから走行中の列車の公式の行先とダイヤの終着駅が1本も食い違わなくなるまで、取得のたびにダイヤを取り直します（安全装置として5時30分まで）。保存したデータで朝を再生すると、平日から平日に変わる朝は最初の列車が現れた4時32分に一致を確かめ、取り直しは1回で済みました。土曜（10月10日）と月曜（10月19日）の朝は、前の日のダイヤであることを見分けて取り直し続け、5時1分に保存されていた新しいダイヤで追いつきました。ただし、**公式のダイヤが何時に新しい日に切り替わるかは確認できていません**。保存したデータには、切り替わる朝の4時半〜5時のダイヤが無いためです。切り替わるまでの間は、前の日のダイヤのままです。
*   **運行状態の推定**：`status` の `"scheduled"` / `"completed"` はダイヤ上の時刻だけで判定します。遅延は考慮しません。正確なのは `"active"`（走行中）だけです。
